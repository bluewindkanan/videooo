# 项目宪法（Project Constitution）

> 定义项目的不可变原则。所有功能开发和架构决策必须遵守这些原则。
> 创建日期：2026-05-05

## 不可变原则

### 原则 1：Evidence-First Delivery（证据先行）

所有实现必须有可追溯的证据链：TDD receipt、可运行测试命令、validation evidence。没有测试覆盖的代码不算完成，没有验证证据的功能不可发布。证据是 go/no-go 决策的唯一依据。

合规检查：
- 每个实现任务都有对应测试。
- 测试可通过标准命令一键运行。
- validation-report.md 包含可追溯的测试和验证证据。

### 原则 2：User-Visible Slice First（用户价值切片优先）

每次交付优先形成用户可感知、可验证的价值切片，而非纯基础设施或内部重构。第一版必须围绕内容团队能完成一个知识分享短视频初稿的真实路径推进。

合规检查：
- 每个 feature.md 的 MVP scope 包含用户可观察行为。
- 首个执行块产出的增量可由内容团队验证。
- 纯基础设施任务必须附属于用户价值切片。

### 原则 3：Simplicity Over Speculation（简约优于猜测）

不为假设的未来需求添加抽象层、配置项、模块划分或流程步骤。口播和产品介绍是扩展方向，但第一版不能因此引入复杂通用编排平台。

合规检查：
- 新抽象必须能被当前知识分享工作流证明必要。
- 不为“以后可能需要”创建空模块或未使用接口。
- design.md 中每个设计决策都可追溯到当前功能需求。

### 原则 4：Use Existing Architecture Directly（直接沿用现有架构）

优先使用项目已有目录结构、helper 和约定。应用代码必须放在 `app/` 下，并与 BeWater 的 `application_root=app` 对齐。

合规检查：
- 新代码路径以 `app/src/...` 为主。
- 如需引入新依赖或新架构模式，design.md 必须说明理由。
- decision-log.md 记录关键架构偏离决策。

### 原则 5：Boundary Validation（边界验证）

用户可见行为必须通过真实边界验证。纯单元测试不足以证明功能完整。视频生产功能至少需要 API、Worker、媒体合成或 Web smoke 级验证。

合规检查：
- 每个用户可见行为至少有一个边界级测试。
- 测试在真实或接近真实环境中运行。
- 功能边界在 design.md 或 tasks.md 中明确定义。

### 原则 6：Workflow Over Editor（工作流优先于编辑器）

本项目优先做标准化视频自动化生产流程，不做通用时间线剪辑器。任何剪辑能力都必须服务于“从输入到可发布初稿”的工作流。

合规检查：
- UI 首先服务任务提交、进度、预览、审核和下载。
- 不把自由时间线编辑作为第一版核心能力。
- 剪辑相关能力必须能减少人工制作时间。

### 原则 7：Reviewable Automation（可审查的自动化）

自动化产物必须可预览、可追溯、可人工小改。第一版不追求完全无人值守，而是追求让人工从生产者变为审核者。

合规检查：
- 生成结果保留中间产物、LLM 原始响应、解析后 JSON 和 Reviewer 问题。
- 失败步骤和质量问题能定位到具体环节或片段。
- 关键产物可被用户查看和下载。

### 原则 8：Rights-Aware Inputs（素材权利边界明确）

第一版允许直接使用用户提供链接素材，但必须明确用户负责素材使用权，系统不承诺自动版权判断。后续若扩展素材搜索或素材库，必须重新设计授权和合规边界。

合规检查：
- 输入界面和文档提示素材使用权责任。
- 不宣传系统能自动解决版权问题。
- 自动联网搜索素材不是第一版默认能力。


### 原则 9：Artifact-First Media Pipeline（产物优先的媒体流水线）

视频生产中的每一步都必须写出可追踪中间产物。不能只有最终视频；文案、分镜、配音、字幕、素材片段、封面、合成日志和 Reviewer 问题都必须能定位、复查和重试。

合规检查：
- 每个 WorkflowStep 都有明确 artifact 输出或明确跳过原因。
- 失败时保留已生成产物和错误上下文。
- Web 端至少能展示关键步骤状态和主要中间产物。
